3. Useful research content is missing from initial HTML on the homepage/project index/network board. Add dated factual explanations and links to authoritative server-rendered catalogues. Keep live enhancement. Unavailable data must never imply zero activity or fabricated success.
4. Separate current central review/testing from future federation governance, funding plans, coin ambitions and the 21,600 proposals. Acceptance is not independent scientific validation. Preserve the public README's claim-verification limits.
5. Add /status to the page map. Consolidate the old /uain-in-60-seconds.html into /about with a permanent redirect. Use truthful lastmod only, omit unknown dates. Unfiltered page N gets its own canonical; filters/searches are noindex,follow and excluded from maps.
6. Measure actual search visibility and dated evidence. robots and machine manifests alone cannot guarantee indexing or AI-search inclusion.

### B. Task eligibility and pagination
Reproduce central-only omission first. Reuse central visibility/claimability, preserve legacy exclusions. ### D. References and initial HTML

### E. Explanatory/evidence pages
Create /about, /how-it-works, /faq, /research, /updates, /updates/{slug}, /governance and /sitemap. Each needs title, description, canonical, one H1, sources and truthful date. ### F. IndexNow
Inspect existing UAIN-only Bing state before key decisions. Reuse configured proof when possible; never guess/rotate credentials. Production key publication is a separate authorized release operation. Verify exact hosted UTF-8 proof at root before notification. Local CLI defaults to dry-run, fixed endpoint and host, rejects HTTP/off-host/credentials/private/filter-spam/malformed URLs, deduplicates, batches <=10,000 and bounds retries. Submit actual published added/changed/deleted URLs from adoption onward, use maps for history. 202 means pending key validation; receipts never promise indexing. No anonymous submission endpoint or deployment integration until local review.
